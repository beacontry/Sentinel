2026-05-29

Optimizer honesty, responsiveness & P&L-percent fixes

A day of making the optimizer's numbers trustworthy, its runs non-disruptive, and trade P&L percentages correct.

Survivorship & out-of-sample integrity

  • Point-in-time S&P 500 membership. The sp500 universe reconstructs date → constituents from Wikipedia's change log (getSP500MembershipResolver() in sp500.ts) and gates GA entries to then-members — removes the membership half of survivorship bias. top50/top150 stay today's-winners lists (no PIT data exists), are labeled biased, and the optimizer defaults to sp500. Residual: fully-delisted names have no free price data, so they still drop out — bias reduced, not eliminated.
  • Mode comparison is now out-of-sample. Every mode is scored on the held-out test window (warm up over full history, trade/record only the held-out segment, PIT-gated). The Optimized row was diverging from the run card (re-simulated 948% vs the run's stored 549% holdout); it now reads the run's stored OOS metrics directly so it always ties to the Top Runs card.

Responsiveness

GA runs in a worker_threads worker (optimizer-worker.ts, esbuild-bundled into the standalone output, spawned from startOptimization). The CPU-bound GA no longer starves the single-threaded event loop — other requests (broker status, polls) used to time out as "Offline" mid-run. Fail-safe: existsSync gate + spawn try/catch fall back to in-process; the esbuild build step is non-fatal. First attempt mis-marked deps external (Cannot find module 'pino' at gen 0); fixed by bundling everything.

Correctness

  • P&L percent used the wrong basis. Recent-trades row and trade-share card divided realized P&L by exit proceeds instead of entry cost basis — a +89% DELL trade ($214.59 → $405.71) displayed as +47%. Now uses cost basis = proceeds − P&L. The share card also mislabeled the exit fill as the entry and never set the exit; both derived correctly now.
  • Tactical proxy de-noised. The mode comparison's plain Tactical bought the first 16 names in map order (alphabetical slice = noise); now ranks by 60-day momentum, top 16. Tactical / Tactical-Smart labeled as simplified SPY-timing proxies (not the live engine).

Migration (idempotent; applied on prod as postgres)

  • 0045_optimization_test_metrics.sql — test_trade_count + test_avg_positions on optimization_runs so the comparison's Optimized row can show trades / time-in-market from stored run metrics (older runs show "—" until re-run).

Six-round defensive bug hunt (31 fixes) + optimizer realism

A sustained find→verify→fix audit across the whole surface. Full itemized report at bug-hunt-report-2026-05-28.html. Each finding was verified against source before fixing — several agent over-flags were downgraded rather than patched. tsc clean, 573/573 tests pass throughout.

Alerts engine rebuild (same day)

The alerts engine had evaluated rules only as a side-effect of GET /api/analyze/[symbol], keyed by symbol not user (a stranger's analyze drove your rule's cooldown; symbols nobody analyzed were never checked), and "crossover" rule types were really level checks.

  • New GET /api/cron/evaluate-alerts (x-cron-secret, market-hours-gated): one data fetch per distinct enabled-rule symbol, evaluates every rule on fresh data. Analyze-route trigger removed.
  • Edge-triggering via alert_rules.last_condition_met (migration 0044): fire on false→true only, re-arm when cleared; pure decideAlert(), 15 unit tests.
  • Real volume_spike (× trailing avg volume) and pct_drop (vs prior close); the hardcoded ×1M / never-set-previousPrice placeholders are gone.
  • Operational TODO: schedule the cron (*/5 * * * * curl with x-cron-secret) — doesn't run until wired up.

Optimizer realism fixes (same day)

Triggered by two TOP150 runs showing 900–1300% on a roughly flat-market window. Three independent issues compounded:

  • Drawdown penalty disabled by a unit bug. blendedFitness did 1 − maxDrawdown / 0.30, but maxDrawdown is a percent, so the term floored to a constant 0.05 for every run — the GA chased raw return with no risk control. Fixed to /30.
  • Both backtesters were frictionless — a tiny per-trade edge compounded into fantasy returns. Added a shared cost model (BACKTEST_COSTS: per-side slippage bps + per-fill commission) to portfolioBacktest and runBacktest.
  • Test-set leakage in GA fitness — the actual root cause. After the two fixes above, a re-run still showed ~800% test ≈ ~813% train. The reason: fitness blended 0.6 × train + 0.4 × test, so the test window was part of the selection objective — the GA optimized the "test" return, making it not out-of-sample (test ≈ train by construction). Fixed to train-only fitness with the test window evaluated once on the winner as a genuine holdout. Expect honest, much-lower test returns now.

Migrations (idempotent; apply on prod as postgres)

  • 0041_congress_dedup_nulls.sql — NULL-safe COALESCE unique index so NULL-ticker congress rows stop duplicating on re-ingest (dedups existing rows first).
  • 0042_trader_status_user_idx.sql — btree index on trader_status.user_id.
  • 0043_forum_replies_parent_fk.sql — self-ref FK ON DELETE SET NULL on parent_reply_id (nulls orphans first).
  • 0044_alert_rules_last_condition_met.sql — edge-triggering column for the alerts engine rebuild above.
Action required: all prior optimizer runs were scored under leakage + broken risk control + frictionless fills. Re-run; don't trust the current ACTIVE preset for live trading.

Deferred items cleanup (PR 21)

The three items the PR 16/17 audit flagged "deferred to focused PR" all shipped tonight while the market was closed. End-of-day count: 567 tests across 40 suites (+9 from earlier PR-19 baseline).

a. Swap-sell planner extraction + integration test

The post-loop swap-sell redeployment decision tree was inlined in runScan as a 90-line block — not directly testable without mocking the entire engine. PR 21a extracted planSwapSellRedeploy() as a pure function returning {attempts, skips, reachedHardCap, reachedExposureCap}. The thin loop in runScan now calls the planner, then executes only the I/O-bound parts (smart filters, canPlaceBuyOrder with sector context, placeEngineOrder, positionMap update). 13 new integration tests pin the decision tree end-to-end with realistic combos (cooldown + pending + exposure + cap interactions). The unit test that landed in PR 17 (backtester-swap-sell-equivalent.test.ts) covers the backtester-side mirror; this one covers the live-engine path.

b. Engine-reboot state persistence

Before tonight, only mode survived a deploy/restart. After PR 21b, the engine writes a JSONB snapshot (trader_engine_snapshot table, migration 0040) at the end of every successful scan covering: position map (TrackedPosition with stops, take-profits, ATR/RSI cache), dailyLoss, dailyNotional, consecutiveLosses, recentOrderTimestamps (rate-limit window), cooldowns, pendingExits, exitRejectionCount + exitSuppressedUntil (PDT suppression), unprotectedSymbols, boot equity snapshot. Hydrated in startEngine after cooldown-from-DB hydration when snapshot is younger than SNAPSHOT_MAX_AGE_MS = 60 min. Versioned payload (v: 1) — future-schema snapshots discard gracefully. Audit row ENGINE_STARTED with origin: "snapshot_hydrate" records the event. Best-effort save — a failed DB write logs but doesn't abort the scan. 8 new tests pin the serialize/deserialize round-trip including Date preservation, version mismatch handling, and tolerant fallbacks on missing optional fields.

c. Orphan scan promise cancellation

Closes audit P1 #6. Each scan now captures myGeneration = ++engine.scanGeneration at start. When runScanGuarded fires a 10-min override and a fresh scan starts, the new scan bumps the counter. The stale scan calls throwIfScanCancelled(engine, myGeneration) at every major yield point (after enforceDailyLossHalt, between per-symbol loop iterations in runScan and runTacticalSmartScan, before the swap-sell post-loop block) and throws ScanCancelledError if its generation no longer matches. Top-level wrappers catch the error and exit cleanly. Non-cooperative HTTP requests already in-flight still resolve to /dev/null — the orphan stops acting on their results. 9 new tests cover the helper + multi-generation lifecycle scenarios.

What's left from the audit deferred list: Nothing. All three items are done. Future-ideas.md updated to remove the entries; CLAUDE.md updated with the new "Cooperative scan cancellation" and "Engine state persistence" sections.

Triggered by a user observation that tactical-smart was outperforming optimized on the live account. Phase 1 — incident response + observability (PRs 1-13)

  • getOrders(100) → getOrders(100, "open") at 5 sites. Alpaca's default status was all, so a churn-heavy account's 100-row response was dominated by filled/cancelled noise — open buys fell off the page, the duplicate-order guard went blind, and 3 identical WDC limits stacked up.
  • PDT-rejected stop placement → new engine.unprotectedSymbols + UI banner. Same-day positions whose stop Alpaca rejects (40310100) used to look protected in the dashboard while the broker had no resting stop.
  • PDT-rejected exit cascade → EXIT_REJECTION_THRESHOLD = 5 + ENGINE_EXIT_SUPPRESSED audit + push notification. APP triggered stop_loss every minute for 60+ min, each rejected, with no escalation. Now suppressed after 5 rejections for 30 min.
  • Standalone stop-sync scheduler — stop-sync-scheduler.ts runs every 5 min independent of scan health. Previously syncBrokerStops only fired at scan tails; hung scans froze broker stops for the whole session.
  • Tactical-smart scan hang fix — TACTICAL_SCAN_SYMBOL_BUDGET_MS = 8min + TACTICAL_MAX_EXTERNAL_SYMBOLS = 50. Screener was feeding 500+ symbols to the active-management loop; at ~1s/symbol (Finnhub-rate-limited) scans took longer than the 15-min cadence and never completed.
  • brokerConnected set in startEngine + new setBrokerConnected helper centralizing transitions with diagnostic log. 96 false-positive broker_disconnect alerts in 24h before the fix.
  • PWA install fix — manifest start_url was redirecting to /login for unauth users; Chrome rejects 3xx start_urls. Changed to /login?source=pwa (200).
  • Take-profit graduation feature — MODE_GRADUATION_DEFAULT + shouldGraduateExit + promoteToGraduationFloor. At pos.takeProfit, lock pos.stopLoss to entry × 1.30 and hold until 2-of-3 weakness signals fire.
  • client_order_id idempotency — every Alpaca placeOrder sends a UUID. Network-hiccup retries can't double-fill anymore.
  • Long Market Value display fix — Alpaca's portfolio_value is an alias for equity; the trader page was showing the same number twice. Now reads long_market_value directly with margin-loan sub-line when cash is negative.
  • Admin per-user dashboard + drilldown — new /api/admin/user-performance + /dashboard/admin/users/[id]. Sortable table with stale-engine warning icons; drilldown shows full broker connection, engine state, performance metrics, daily P&L, last 50 trades, last 25 audit events.

Phase 2 — optimized mode Option 2 (PR 14)

User observation: tactical-smart producing big runners (DELL +42%, MU +37%) while optimized produced steadier, smaller positions. Root cause was the strategy frame, not the GA params themselves. Brought optimized to capability parity while preserving its distinct character.

  • Graduation enabled for optimized — GA-tuned takeProfitAtrMult becomes a graduation point, not a hard exit. Lets runners ride past training-window-fit exit levels.
  • Screener-fed universe — runScan now uses selectExternalSymbolsForTactical(engine.externalSignals, SCAN_UNIVERSE). Top-50 by confidence, BUY/STRONG_BUY only.
  • Swap-sell post-exit redeploy — new MODE_SWAP_SELL_DEFAULT + deferred-candidates list. When an exit fires during the per-symbol loop, freed slots get redeployed into the top deferred STRONG_BUYs same-scan.

Optimized retains: per-symbol GA-tuned params, fixed position sizing, finite hold periods. Tactical-smart keeps: inverse-vol weighting, 999-day hold, pair-wise swap-sell.

2026-05-13

Reliability fixes

Three targeted fixes from a duplicate-order incident on a single user (SNDK) + getOrders failure-mode tightening + journal v2 hook.

Scan re-entrancy guard

The scan scheduler previously used a bare setInterval(() => scanFn().catch()). When a scan took longer than the tick interval (slow broker, large universe), the next tick fired while the previous scan was still in flight. Both concurrent scans called client.getOrders() independently — and because Alpaca's orders endpoint has hundreds-of-ms eventual consistency, the second scan's pendingBuySymbols set frequently missed the first scan's order. Result: both scans passed the duplicate-buy guard and placed identical limit orders sub-second apart. User reported as "two SNDK buys at the same price/qty/age."

Fix: closure-local scanInFlight flag flipped before scanFn() and cleared in .finally(). .finally() guarantees the flag clears even if scanFn throws. Belt: a 10-minute stale-flag watchdog overrides the flag if for some reason it stayed set (process crash mid-promise, runtime weirdness) so a wedged engine self-recovers within two intraday ticks. Same guard applied to the 1-minute exit-check interval.

getOrders failure: now aborts scan

Previously a try { ... } catch {} silently swallowed errors fetching open orders. The scan continued with an empty pendingBuySymbols set — going blind on duplicate-order detection. Now all three BUY paths (runScan, runTacticalScan, runTacticalSmartScan) log a warning, push a user-visible error, and abort the BUY portion of the scan when getOrders fails. Exits + position-map sync already happened before the getOrders call, so the abort is safe for stop-loss management.

Journal v2 hook in reconciler

When reconcilePendingTrades transitions a row from PENDING to FILLED, it now also calls createAutoJournalStub() (fire-and-forget, never throws). Inserts a journal entry pre-filled with the trade mechanics (symbol, action, fill price, P&L, signal) plus leading questions ("Why am I taking this trade?" for entries, "What's the lesson?" for exits). Idempotent via the journal_auto_trade_uniq partial unique index (migration 0032) — re-runs no-op. User opens the journal page and fills in the WHY; blank-canvas friction removed.

Marathon updates (Phases 1-4)

Post-launch hardening pass. Items here augment the engine ruleset's relevant sections; cross-references CLAUDE.md's 6-phase retrospective for commit SHAs.

Phase 1 — money bugs from UI-lie audit

  • canPlaceBuyOrder() is async + takes a fresh account snapshot. Refreshes the wash-sale symbol set before the wash-sale check; re-runs evaluatePdtState before the PDT check. A 2nd day-trade in a 15-min window or a same-scan losing-close-then-re-entry now correctly evaluates against live state instead of scan-boundary state.

  • bootEquity re-snapshots at every new trading day across both remaining scan paths. The 50% equity-collapse tripwire stays calibrated as the account grows organically.
  • tripSafeguardHalt() writes halted=true to trader_daily_pnl immediately so the dashboard reflects halts on the next fetch.
  • Dashboard todayPnl response carries source + staleSeconds so the UI can render staleness honestly instead of silently mixing broker intraday with DB snapshot.

Phase 2 — frozen-value cleanup

  • syncPositionMapFromBroker() resets pos.peakPrice = currentPrice when broker qty drops > 5% (partial close — trail recalibrates from post-close size).
  • Strategy params refresh per sync — strategy edits propagate to existing positions instead of being frozen at entry-time values.
  • Take-profit recompute when strategy takeProfitPct changes — existing positions get the new target.

Phase 3 — live-trading safeguards

  • 5 capital circuit breakers: daily loss halt, consecutive losses halt, broker-unreachable halt, account-mismatch halt, equity-collapse halt. Every halt writes a hash-chained audit row.
  • Account-switch detection — broker account number + boot equity captured at startEngine(). Mid-session change → halt.
  • Order rate limit — 30 orders / 60s sliding window per engine. Prevents runaway loop scenarios.
  • Daily notional cap — rejects BUYs exceeding maxDailyNotionalPct × bootEquity.

Phase 4 — Phase 5 (personalized live protections)

  • §475(f) MTM election — self-attested via Trader → Tax election card. Disables wash-sale tracking when elected (MTM exempt from §1091).
  • Wash-sale protection — blocks BUYs on symbols with a losing exit within the last 31 calendar days. Symbol-level, not lot-level — over-conservative but simpler.
  • PDT protection — auto-detected from account.equity < $25,000. Blocks BUYs (not SELLs) when pdtVulnerable && daytradeCount >= 3.
