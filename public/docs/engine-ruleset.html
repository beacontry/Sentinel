Signal Generation

All components — engine, optimizer, screener, mode comparison — use the same signal function: analyzeBars() from the unified indicator pipeline. In optimized mode, the engine passes GA-tuned signal params (EMA periods, RSI thresholds) through the pipeline. All other modes use defaults.

Indicators

VWAP EMA crossover (9/21, tunable) RSI 14 (30/70, tunable) SMA (20) SMA (50) MACD (12/26/9) Volume (1.5× avg)

BUY Signal

Fires when bullish count exceeds bearish count by 2+ (minimum 4 bullish indicators):

  1. Price above VWAP (bullish positioning)
  2. Fast EMA > slow EMA (uptrend)
  3. Fresh EMA crossover within lookback window
  4. RSI below oversold threshold or above 55 (momentum)
  5. Price above SMA(20)
  6. MACD histogram positive

STRONG_BUY Upgrade

A BUY is upgraded when both of these confirm:

  • Volume exceeds 1.5× the 20-bar average
  • Price aligned with SMA(50)
ℹ SELL and STRONG_SELL are the mirror: bearish indicators dominate. Same thresholds, opposite direction.
03

Exit Logic

Positions close the moment any single exit condition fires. First trigger wins.

ℹ Dual cadence. Exits are checked twice: every 15 min in the main scan (uses last-bar close), and every 1 min in runExitCheck() using a live quote. The 1-min loop now runs in every mode — not just intraday — so trailing stops track the live peak instead of yesterday's close. A double-sell guard (pendingExits set on engine state) prevents the two intervals from racing on the same symbol.
◼ Fixed Stop Loss— price drops below entry × (1 − stopLossPct)
◼ Dynamic Trailing Stop— price drops below peak × (1 − trailPct)
◼ Take Profit— price exceeds entry × (1 + takeProfitPct)
◼ Sell Signal— technical analysis generates SELL or STRONG_SELL
◼ Hold Period Expired— position held longer than max hold bars

Exit logic varies dramatically between mode families. Signal-based modes manage each position independently with multiple triggers. Tactical modes treat the portfolio as a unit — all in or all out based on SPY health.

Optimized GA — Individual Exits

Each position is managed independently. On every scan (~15 min), the engine checks all 5 exit conditions in priority order. First trigger wins. SPY health filter only blocks new entries — it does NOT force exits of held positions.

  1. Stop loss — price ≤ entry × (1 − stopLossPct). GA-tuned, typically ~8.5%
  2. Take profit — price ≥ entry + ATR(14) × multiplier (adaptive) or fixed % fallback
  3. Trailing stop — price ≤ peak × (1 − dynamicTrailPct). Tightens exponentially as profit grows
  4. Hold period — position held ≥ holdPeriod trading days. GA-tuned, typically ~33 days
  5. SELL/STRONG_SELL signal — analyzeBars() with GA-tuned signal params scores bearish

Tactical Smart — Market Regime + Swaps

Two layers of exit logic:

Layer 1 — SPY Weakness (portfolio-wide)

SPY closes below its 20-day SMA for 3 consecutive days → sell ALL positions immediately at market. No graduated exit. This is the primary exit mechanism and overrides everything.

Layer 2 — Active Management (while SPY is healthy)

While invested, scans every 15 min for held positions with SELL/STRONG_SELL signals (weak stocks). Sells them at market and buys STRONG_BUY replacements. Can also add new positions if cash is available (up to 1.5× maxPositions). Individual stop/TP/trail levels exist (12% / 50% / 11.7%) but with a 999-day hold period, SPY weakness almost always fires first.

Tactical — Pure Market Timing

Simplest exit of all three modes. Only trigger: SPY below 20-day SMA for 3 consecutive days → sell ALL positions at market. No individual position management, no stop losses, no trailing stops, no sell signals, no swapping. Full in or full out — the only decision is SPY trend direction. Re-entry when SPY recovers above 50-day SMA.

ℹ Key distinction: In Optimized GA, a SELL signal exits the position. In Tactical Smart, a SELL signal swaps it for a stronger stock. In Tactical, sell signals are not used at all.

Dynamic Trailing Stop

The trailing stop tightens exponentially as profit increases, locking in more gains as the trade runs. Floor is always 2% — the stop never gets tighter than that.

trail = 2% + (baseTrail − 2%) × e−3 × profitPct

5%10.3%~0%
10%8.6%~1.4%

30%3.7%~26.3%
50%2.4%~47.6%
✓ At 50% profit, the trailing stop is only 2.4% wide — locking in at least 47.6% of the trade.

Pre-Buy Safety Filters

Every buy signal must pass through ten sequential gates before an order reaches the broker. If any gate blocks, the signal is discarded.

1
Market Hours
Only trade 9:30 AM – 4:00 PM ET, Monday through Friday.
Skip entire scan outside hours
2
SPY Market Health
SPY must be above its 20-day SMA. If the broad market is weak, no buys.
Block ALL buy signals when SPY < SMA(20)
3
Earnings Blackout
Don't buy within 5 trading days of an earnings announcement. Avoids binary events.
Skip symbol if earnings within [−1, +5] days
4
Relative Strength
Don't buy stocks with negative 60-day momentum (down more than 5%). Only buy strength.
Skip symbol if 60-day return < −5%
5
News Sentiment
Don't buy when news sentiment is strongly bearish (Finnhub bullish% below 30%).
Skip symbol; neutral fallback if API unavailable
6
Signal Cooldown
Don't re-buy the same symbol within 2.5 hours. Prevents chasing the same signal. Stored in a dedicated cooldowns map on engine state so the 150-min window is actually enforced (the previous implementation piggybacked on a queue that flushed entries at 30 min, silently collapsing the cooldown).
Skip if same symbol had a buy signal within 150 min
7
Max Positions
Don't exceed maxPositions from risk settings. BUY signals are blocked when open positions ≥ maxPositions. STRONG_BUY signals can exceed maxPositions by up to 50% (e.g., maxPositions=13 → cap of 19). Exposure and cash checks still apply.
Block BUY if at limit; allow STRONG_BUY overflow up to 50%
8
Max Portfolio Exposure
Total exposure cannot exceed the configured limit from risk settings.
Skip if adding this position exceeds maxExposure
9
Daily Loss Halt
If daily losses exceed the configured % of equity (default 2%), halt everything.
Halt engine, cancel ALL pending orders
10
Pending Order Check
Don't buy a symbol that already has a pending buy order on the broker. Engine fetches open orders from Alpaca at each scan cycle.
Skip symbol if pending buy order exists (new, accepted, partially filled, held)

Entry Orders

  • Type: Limit order, 0.1% above current price. Plain order — not a bracket. Stops and take-profits are managed by the engine, not by Alpaca-side OCO legs.
  • Time in force: Day (expires at market close)
  • Broker-side stop: Placed separately via syncBrokerStops() on the next scan after the buy fills. Acts as a crash-safe fallback if the engine goes offline.

Position Sizing

  • Per position: positionPct × total equity (default 15%)
  • Max shares: capped by maxPositionSize from risk settings
  • Max positions: from risk overrides (default 16), STRONG_BUY can overflow by 50%

Exit Orders

  • Type: Market order for immediate execution
  • Trigger: Any exit condition met during scan
08

Safety Systems

⚠ Live trading is env-gated. The engine refuses to start against a live broker connection unless ALLOW_LIVE_TRADING=1 is set in the server environment. Even when unlocked, every live boot fires a warn-level log, captures an audit row with environment="live", and the Trader UI shows a persistent red LIVE banner. See section 16 (Live Trading Mode) and section 20 (Going Live & Rollback).

Dual-Layer Stop Protection

Two layers of stop orders protect positions depending on whether the engine is running:

  • While running (protective stops): Gain-aware GTC stop orders on Alpaca using max(disasterStop, trailingStop, fixedStop) with current broker price as peak. Positions with unrealized gains get tight trailing stops, not a flat 18% from entry. syncBrokerStops() ratchets stops up every scan cycle as price rises.
  • When stopped (safety stops): Tighter strategy-level GTC stops (~8.5% from optimizer) placed on Alpaca. More protective since the engine won't be managing exits.
  • On engine start: Cancels old stops → places gain-aware protective stops.
  • While running: syncBrokerStops() updates stops every scan to match dynamic trailing (2% floor, exponential decay from base).
  • On engine stop: Cancels protective stops → places ~8.5% safety stops.

Auto-Restart After Deploy

On container start, instrumentation.ts waits 5s for the DB pool, then runs bootEngines() which iterates every user with an active broker connection and calls autoStartIfNeeded(). The engine resumes without waiting for a user to open the dashboard. Transient broker/DB errors retry up to 3 times with 2s/4s backoff before giving up at error level.

Graceful Shutdown

SIGTERM and SIGINT handlers call shutdownAllEngines() — for each running engine, it clears the scan/exit-check intervals and runs placeSafetyStops() so every position has a tighter GTC stop on Alpaca before the process exits. Hard 8s budget, well under podman's 10s grace period — if the broker is slow, the handler force-exits rather than block the rebuild.

Mode Persistence

The current mode is saved on every heartbeat as paper:optimized, paper:tactical, etc. Auto-restart reads this to resume the correct mode. Valid modes: conservative, moderate, optimized, aggressive, intraday, tactical, tactical-smart.

Daily-Loss Halt & Auto-Recovery

When daily realized losses exceed dailyLossPct of equity, the engine sets halted=true and stops opening new positions. On the next trading day's first scan, the date-rollover block clears the halt automatically and prunes the daily-loss error from engine.errors — no manual restart needed. Applies to all three scan functions (runScan, runTacticalScan, runTacticalSmartScan).

Long-Only Enforcement

The engine never opens shorts — entry logic only fires on BUY/STRONG_BUY. If a short shows up on the broker (manual order, external tool), syncPositionMapFromBroker() filters it out so long-only stop math doesn't get applied wrong-direction to it. The screener also no longer pushes SELL/STRONG_SELL into the engine queue.

Exit Race Protection

The 1-min live-quote exit check and the 15-min main scan both call placeOrder({side:"sell"}). A pendingExits: Set<symbol> on engine state gates both code paths — add() before placing the sell, delete() in finally. Prevents the double-sell that previously surfaced as Alpaca rejecting a second order with "insufficient qty".

Tactical Modes

Tactical modes don't pick individual stock signals. They use SPY as a market barometer — fully invested when the market is trending up, fully out when it breaks down.

Tactical (Equal Weight)

Entry — Full In

SPY closes above its 50-day SMA. Buy equal-weight positions across the universe, up to maxPositions.

Exit — Full Out

SPY closes below its 20-day SMA for 3 consecutive days. Sell ALL positions at market. No graduated exit — full in or full out.

Tactical Smart (Scored Entry)

Same SPY timing, but stock selection is scored and weighted:

  • Momentum — 3-month return × 300
  • Signal score — STRONG_BUY = 4, BUY = 2, HOLD = 0, SELL = −2
  • Screener boost — external STRONG_BUY +3, BUY +1
  • Confidence — × 2 multiplier

Position sizing uses inverse volatility weighting — stable stocks get more capital. Stocks with negative momentum are skipped entirely.

Active Management (While Holding)

When invested and SPY is healthy, the engine actively manages the portfolio every 15 minutes:

Swaps — Sell Weak, Buy Strong

Scans held positions for SELL/STRONG_SELL signals and the universe for STRONG_BUY candidates not already held. Sells weak positions at market, buys replacements at limit (0.1% above current price).

Additions — Deploy Unused Cash

Remaining STRONG_BUY candidates can be added if cash is available. Respects 1.5× maxPositions hard cap (same as STRONG_BUY overflow) and max exposure limit.

ℹ Top 5 STRONG_BUY candidates are logged to the signals table for visibility, even if not acted on.

Exit

Same as Tactical — full exit on SPY weakness (below 20-day SMA for 3 consecutive days).

Daily P&L Tracking

Both Tactical and Tactical Smart modes call upsertDailyPnl on each scan cycle. Daily P&L is recorded for the P&L Calendar and performance tracking.

Screener vs Engine Authority

The screener only pushes BUY/STRONG_BUY signals to the engine — never SELL signals. Once a position is entered, it is managed entirely by the engine's exit logic. The screener has no influence on exits, stop losses, or take profits. If the screener and engine disagree on a stock (they use different signal params), the engine's analysis controls the position.

GA Diversity Mechanisms

Diversity is purely a GA search mechanism — it has no effect on live trading. It controls how the optimizer explores the 8-dimensional parameter space.

  • Diversity measurement: Average normalized distance across sampled parameter pairs (0 = clones, ~1 = max spread)
  • Adaptive mutation: Rate scales from 10% (healthy, diversity > 0.35) → 20% (baseline) → 50% (collapsed, diversity < 0.10)
  • Random immigrants: 5% of each generation replaced with fresh random individuals
  • Stagnation restart: After 8 gens without improvement, inject 15% immigrants + max mutation
  • Convergence chart: Best, average, and diversity lines shown per generation on dashboard

Live Trading Mode

The engine code path is identical between paper and live. The only environment-specific branches are: the Alpaca client constructor (picks api.alpaca.markets vs paper-api.alpaca.markets), the boot-time env gate, and the UI banner. Signal generation, order construction, stop calculation, and all five circuit breakers (section 17) operate identically in both environments.

⚠ What carries over from paper: signals, strategy, risk-profile sizing, all engine safeguards. What does NOT carry over: fill rate, slippage, partial fills, order rejection patterns, settlement timing, PDT lock, wash sales. Outcomes are at the broker/market layer, not the engine.

Boot Gate

At startEngine(), the engine resolves the active broker connection and inspects its environment field. Behavior:

  • environment === "paper" → engine starts normally.
  • environment === "live" AND ALLOW_LIVE_TRADING !== "1" → refused. Returns a specific error to the UI naming the env var that must be set. Emits engine.live_blocked audit event with the connection id.
  • environment === "live" AND env unlocked → engine starts; warn-level log; engine.started audit row includes metadata.environment="live" and boot equity snapshot; UI flips on the persistent red LIVE banner.

Capital Circuit Breakers

Five auto-halt or auto-block conditions layered on top of the existing safety systems (section 08). All operate identically in paper and live. Each emits a distinct audit reason so the audit viewer can filter cause.

1. Daily Notional Cap

01
Gross BUY notional / day ≤ maxDailyNotionalPct × bootEquity
Sum of every BUY's qty × limitPrice tracked on engine state (engine.dailyNotional); resets at day rollover. Default cap 100%, configurable per user in risk profile (suggest 50% on a small account).
Block BUY; audit order.rejected reason=daily_notional_cap_exceeded

2. Order Rate Limit

02
Max 30 orders / 60s sliding window per engine
Timestamps of every BUY and SELL pushed onto engine.recentOrderTimestamps; pruned on each gate check. Defense against signal-storm bugs that could fire dozens of orders in seconds.
Block; audit order.rejected reason=order_rate_limit_exceeded

3. Broker Auto-Halt

03
5 consecutive getPositions() failures → halt
Tracked via engine.consecutiveBrokerFailures. Replaces the older log-only behavior — stale position data is more dangerous than not trading.
Halt engine; audit engine.halted reason=broker_unreachable; user must Stop+Start to clear

4. Account-Switch Detection

04
Boot snapshot mismatch on equity or account number
At startEngine() the engine captures {equity, accountNumber} from getAccount(). Every scan compares the live snapshot: different accountNumber → halt; equity drop > 50% → halt. Catches "wrong API key pasted" and "connection update mid-session swapped accounts" disasters.
Halt; audit reason=account_mismatch or equity_collapse; requires explicit Stop+Start to acknowledge

5. Consecutive-Loss Halt

05
N losing trades in a row → halt
After every closed trade, recordTradeResult(engine, pnl) increments engine.consecutiveLosses on losses, resets on any winner (zero P&L doesn't reset — rare exact-even close). Default threshold 5, configurable in risk profile (suggest 3 for small live accounts).
Halt; audit reason=consecutive_losses with count + threshold
✓ Gate ordering inside canPlaceBuyOrder(): wash-sale → PDT → daily notional → rate limit. Cheapest checks fire first; the first reason found is what the audit log records. Sells (exits) are never blocked by these gates — exiting a position takes priority over any safeguard.

Tax & PDT Protections

Three personalized protections that vary by account state and user election. All can be observed/toggled from the Trader page.

§475(f) MTM Toggle

Trader page renders a "Tax election" card with a single checkbox: "I have elected §475(f) Mark-to-Market". Writes to the existing user_tax_status table via PUT /api/tax-status. The engine reads this at startEngine() via loadTaxStatus(userId).

  • Unchecked (default): Wash-sale protection ON.
  • Checked: Wash-sale protection OFF. MTM traders are exempt from §1091, so the engine doesn't block re-entries on losing exits.
⚠ Self-attestation only. Sentinel does not file or validate the election with the IRS. The election deadline is April 15 of the prior tax year (or as a new entity). Check the box only if you actually filed.

Wash-Sale Protection

When enabled (MTM unchecked), the engine blocks BUYs on any symbol with a losing exit in the last 31 calendar days. One day past the IRS 30-day rule for safety margin.

  • Source query: SELECT DISTINCT symbol FROM trader_trades WHERE user_id=? AND action IN ('SELL','manual_close') AND pnl < 0 AND created_at > now() - 31 days
  • Cached for 5 min on engine state as washSaleBlockedSymbols: Set<string> — one batched DISTINCT query per refresh, O(1) lookup per BUY.
  • Symbol-level, not lot-level: one partial losing close blocks the whole ticker for 31 days. Over-conservative, but simpler and safer than per-lot accounting.
  • Manual closes count: the Trader UI's Flatten command logs action="manual_close" in trader_trades; those also feed the wash-sale set.
  • Does NOT catch: manual BUYs through Alpaca's own app (engine sees them only after position sync, too late to block); "substantially identical" ETFs (SPY ↔ IVV); different share classes (GOOG vs GOOGL).

PDT Protection (Pattern Day Trader)

Auto-detected from account.equity < $25,000. Reads broker-reported daytrade_count and pattern_day_trader fields from getAccount() on every scan, evaluated by evaluatePdtState(engine, account).

Three behaviors:

  1. Boot mode-refusal. If isPdtVulnerable(bootAccount) AND mode is intraday, startEngine() returns a clear error naming the equity threshold and acceptable modes. Tactical/tactical-smart/conservative/moderate/optimized are still allowed — they're swing-oriented.
  2. Mid-session re-evaluation. Every scan, evaluatePdtState() reads live equity and daytradeCount. Transition not-vulnerable → vulnerable emits one engine.pdt_vulnerable audit event (informational, no halt) and flips the Trader page warning panel.
  3. Buy-block. When pdtVulnerable AND daytradeCount >= 3 (one shy of the 4-trade PDT flag), all new BUYs blocked. Audit reason pdt_protection. SELLs always allowed — exits override PDT, since losing a position to a lock is worse than the lock itself.
ℹ Note: Alpaca uses previous business day's closing equity for the actual PDT flag, not real-time. Sentinel treats equity < $25k as vulnerable in real-time, which is intentionally more conservative.

Audit Log

Append-only, hash-chained, tamper-evident record of every privileged action. Schema in drizzle/0016_audit_log.sql; helper in src/lib/audit.ts; admin viewer at /dashboard/admin/audit.

Row Shape

One row per event with the actor, action, resource, IP / user-agent, structured metadata, and the hash-chain pointers:

id (bigserial) prev_hash (text) created_at (timestamptz) hash (text) actor_user_id (uuid) ip (text) actor_email (text) user_agent (text) actor_role (text) metadata (jsonb) action (text) resource_type (text) resource_id (text)

Hash Chain

Each row's hash is the SHA-256 of its predecessor's hash plus its own canonical fields:

hash = sha256( prev_hash || \0 || created_at.toISOString() || \0 || actor_user_id || \0 || action || \0 || resource_type || \0 || resource_id || \0 || canonical_json(metadata) )

NUL byte separator cannot occur in any UTF-8 string field, preventing field-confusion / length-extension attacks. canonical_json sorts keys at every depth so equivalent objects produce identical hashes.

The genesis row's prev_hash is the literal string "GENESIS". Tampering with any row breaks the chain at that row when verified.

Write Path

writeAudit() opens a Postgres transaction, takes pg_advisory_xact_lock(8493920100) (auto-released on commit), reads the tail row's hash, computes the new hash, inserts. Concurrent writers serialize on the advisory lock so the chain can't fork.

The helper never throws — failures log and return null. Audit problems must not cascade into request failures (rather lose a log line than refuse a legitimate trade).

What's Logged

Verification

The admin viewer at /dashboard/admin/audit has a "Verify chain" button that calls POST /api/admin/audit/verify. The endpoint walks every row in id order, recomputes each hash, and reports either "intact" or the first row where the chain breaks (with stored vs expected hash). Walk takes ~2s per 100k rows.

Run it after any unusual incident, before any major decision based on the trade history, or as a periodic sanity check.

Going Live & Rollback

Going Live

  1. Tighten risk profile (Trader page → Risk Settings). For a $5k cash-only account: maxPositionPct=25−33%, maxDailyLossPct=2%, maxDailyNotionalPct=0.5, maxConsecutiveLosses=3, maxPositionSize=20, maxExposureMultiplier=1.0.
  2. Add live broker connection (Settings → Add Broker). Environment = Live, paste live Alpaca API key+secret, type "LIVE" in the confirmation input, Test, Save.
  3. Deactivate paper connection (Settings → toggle isActive=false on the paper row). Engine then resolves only the live one.
  4. Flip the env-gate on the droplet:
    echo 'ALLOW_LIVE_TRADING=1' | sudo tee -a /opt/apps/sentinel/.env sudo podman stop sentinel-app && sudo podman rm sentinel-app sudo podman run -d --name sentinel-app --network=host \ --env-file /opt/apps/sentinel/.env \ -e NODE_ENV=production -e HOSTNAME=0.0.0.0 -e PORT=3010 \ -e NEXT_TELEMETRY_DISABLED=1 -e CACHE_DIR=/data/cache \ -v /opt/apps/sentinel/cache:/data/cache:Z \ --restart always -m 2g \ ghcr.io/ixiondt/sentinel:latest

    podman restart does NOT re-read env-file — must stop && rm && run.

  5. Start engine (Trader page → Start) in a swing mode (NOT intraday — engine refuses if equity < $25k). Watch the persistent red LIVE banner appear, audit log fill with engine.started (metadata.environment="live"), and the boot equity snapshot get captured.

Rollback — Three Off-Ramps

A. Env-only rollback — "live went badly, go back to paper"

Cheapest path. No code changes, no rebuild, no DB changes. Clear ALLOW_LIVE_TRADING in /opt/apps/sentinel/.env, recreate container (same podman run as above). Engine immediately refuses live boots; live broker row stays in DB for easy re-enable.

B. Code revert — Phase 3 false halts / audit too slow

git revert phase commits in reverse order (4 → 3 → 2). Migrations stay applied (additive). Do not revert Phase 1 — it would re-introduce the silent-plaintext decrypt fallback. Phase 4 depends on Phase 2 (audit viewer reads the table), so revert 4 before 2.

C. Migration drop — only when table is corrupted

Almost never needed. Always pair with the matching code revert or loadRiskLimits() crashes on every scan. For audit_log: TRUNCATE audit_log is the clean reset (next write becomes new genesis). Do NOT DELETE WHERE id < N — that breaks the hash chain forever.

What to Watch in the First Hour

  • Red LIVE banner missing. engine.environment not captured at boot. Stop engine, check the engine.started audit row metadata; restart engine.
  • PDT panel missing at <$25k. Alpaca didn't return daytrade_count / pattern_day_trader. Check live account.equity matches what you expect.
  • Many order.rejected rows with insufficient_buying_power. Live broker margin/cash strictness. Tighten positionPct if persistent.
  • Chain verify reports a break. Stop immediately. Do not trade. Investigate before resuming — this is the critical evidence trail.
  • First buys filling at unexpected prices. Real slippage between paper assumption and live execution. Document the delta — that's your paper-to-live tax.

System Configuration table (migration 0030)

Encrypted server-wide secrets that admins can rotate from /dashboard/admin/system-config without touching the droplet. Schema is just (key TEXT PRIMARY KEY, value_encrypted TEXT, updated_by UUID, updated_at TIMESTAMPTZ). Values are AES-256-GCM ciphertext via src/lib/crypto.ts (no plaintext fallback). Allow-list of known keys enforced in code: GROQ_API_KEY, FINNHUB_API_KEY, ANTHROPIC_API_KEY — admins cannot silently overwrite arbitrary env vars from the UI.

Resolution order at runtime

  1. 60s in-memory cache
  2. DB row (decrypted)
  3. process.env[<key>] fallback — preserves "works locally without DB row"
  4. null

Admin UI behaviors

  • Each known key shows a last-4-char mask, source badge (DB / ENV fallback / Not set), updated-by and updated-at metadata.
  • [Test] button hits the live provider with a 1-token ping using the candidate key (Groq /chat/completions, Finnhub /quote?symbol=AAPL, Anthropic /messages). Candidate value is not persisted.
  • [Replace] modal accepts a paste, runs Test-before-save, then Save (encrypts + upserts + writes hash-chained SYSTEM_CONFIG_UPDATED audit row with metadata {key, hadOldValue, valueLength} — never the value itself).
  • Plaintext values are never returned by any API or displayed in the UI after save.

Caveats

  • The Finnhub client (src/lib/finnhub.ts) is a singleton that reads its API key field once at process boot. Rotating FINNHUB_API_KEY via the admin UI requires an app restart for the trading engine + per-symbol routes (news, sentiment, recommendations, fundamentals) to pick up the new value. The LLM path is fully async and refreshes within the 60s cache window.
  • API key store is server-wide — one Groq key serves every user. Per-user overrides are deferred design in docs/future-ideas.md.

Adaptive Engine Mode (Phase 8)

EngineMode now includes "adaptive" (8th option). When a user selects adaptive, the engine reads market regime at each scan boundary and runs as one of conservative / moderate / optimized / aggressive / tactical underneath. The user-selected mode stays "adaptive"; strategy decisions go through getActiveMode(engine) which returns the effective base mode.

Regime classifier

Pure function in src/lib/market-regime.ts. Input: { vix, spyPrice, spyMA50, spyMA200, breadthScore? }. Output: { regime, recommendedMode, reasons }.

Regime rules (v1)

  • risk_off → conservative. VIX > 28 OR SPY < SMA50
  • neutral → moderate. 18 < VIX <= 28 AND SPY >= SMA50
  • risk_on → optimized. VIX <= 18 AND SPY > SMA50
  • strong risk_on → aggressive (live only). VIX <= 14 AND SPY > SMA200 AND breadth > 75

Never auto-selected: intraday (PDT-sensitive at <$25k), tactical-smart (already adaptive in its own way), adaptive itself (self-reference loop).

Engine wiring

refreshAdaptiveMode(engine) runs at the top of each scan path (main, tactical-smart, intraday). Fetches ^VIX + SPY bars via the existing market-data provider, computes SPY SMA50/200, calls detectMarketRegime, sets engine.effectiveMode + engine.adaptiveRegime. Emits ENGINE_MODE_SWITCHED audit row only when effectiveMode actually changes scan-to-scan.

Backtester

runBacktest(symbol, bars, ..., mode?, marketContext?) accepts optional mode + marketContext: { spyBars, vixBars }. When mode === "adaptive" AND marketContext provided, the backtester re-resolves the effective config per bar (looks up SPY/VIX for that date, runs the classifier, swaps BacktestConfig). Returns modeTimeline: { date, mode }[] so the UI can visualize regime swings.

Mode-compare page

/dashboard/backtest/mode-compare?symbol=AAPL runs all 6 comparable modes (5 base + adaptive; intraday + tactical-smart excluded) in parallel via Promise.allSettled. Returns stats + equity curves + adaptive's modeTimeline.

Trader page status banner

When running adaptive, two lines under the controls: a standard "Running (adaptive) · PAPER · N scans" line, plus an adaptive-specific second line showing the effective mode + regime: "Adaptive — currently optimized · VIX 18.2 · SPY +1.2% vs SMA50 · risk_on".

Failure handling

If VIX/SPY fetch fails, engine keeps the previous effectiveMode (does NOT halt — adaptive is a meta-decision, not a safety check). Logs a warning.

Live vs backtest difference

Live mode uses VIX + SPY + breadth (a full breadth scan = 50 stocks × N days, too expensive to replay historically). Backtest replays VIX + SPY only — the strong-risk-on → aggressive bump simply doesn't fire in backtest. Defensible simplification.

Reliability fixes (2026-05-13)

Scan re-entrancy guard

The scan scheduler previously used a bare setInterval(() => scanFn().catch()). When a scan took longer than the tick interval (slow broker, large universe), the next tick fired while the previous scan was still in flight. Both concurrent scans called client.getOrders() independently — and because Alpaca's orders endpoint has hundreds-of-ms eventual consistency, the second scan's pendingBuySymbols set frequently missed the first scan's order. Result: both scans passed the duplicate-buy guard and placed identical limit orders sub-second apart. User reported as "two SNDK buys at the same price/qty/age."

Fix: closure-local scanInFlight flag flipped before scanFn() and cleared in .finally(). .finally() guarantees the flag clears even if scanFn throws. Belt: a 10-minute stale-flag watchdog overrides the flag if for some reason it stayed set (process crash mid-promise, runtime weirdness) so a wedged engine self-recovers within two intraday ticks. Same guard applied to the 1-minute exit-check interval.

getOrders failure: now aborts scan

Previously a try { ... } catch {} silently swallowed errors fetching open orders. The scan continued with an empty pendingBuySymbols set — going blind on duplicate-order detection. Now all three BUY paths (runScan, runTacticalScan, runTacticalSmartScan) log a warning, push a user-visible error, and abort the BUY portion of the scan when getOrders fails. Exits + position-map sync already happened before the getOrders call, so the abort is safe for stop-loss management.

Journal v2 hook in reconciler

When reconcilePendingTrades transitions a row from PENDING to FILLED, it now also calls createAutoJournalStub() (fire-and-forget, never throws). Inserts a journal entry pre-filled with the trade mechanics (symbol, action, fill price, P&L, signal) plus leading questions ("Why am I taking this trade?" for entries, "What's the lesson?" for exits). Idempotent via the journal_auto_trade_uniq partial unique index (migration 0032) — re-runs no-op. User opens the journal page and fills in the WHY; blank-canvas friction removed.
