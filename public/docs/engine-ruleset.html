Signal Generation

The trade-decision pipeline is layered. Every component starts with the same technical core — analyzeBars() from the unified indicator pipeline — which produces a signal + confidence from EMA / RSI / MACD / ATR. The live engine then calls analyzeHybrid(), which optionally adjusts confidence (and occasionally the signal direction) using Finnhub sentiment, options flow, analyst recommendations, and AI scoring. Trader-tier users get the Finnhub layers; Premium users additionally get AI scoring; free-tier doesn't reach the engine. In optimized mode the GA-tuned signal params (EMA periods, RSI thresholds) flow through to analyzeBars(); all other modes use defaults. Screener + optimizer + backtest mode-compare call analyzeBars() directly without the hybrid layers (sentiment/options/analyst run through Finnhub's 60-req/min rate limit and would serialize the S&P 500 universe scan).

Indicators

VWAP EMA crossover (9/21, tunable) RSI 14 (30/70, tunable) SMA (20) SMA (50) MACD (12/26/9) Volume (1.5× avg)

BUY Signal

Fires when bullish count exceeds bearish count by 2+ (minimum 4 bullish indicators):

  1. Price above VWAP (bullish positioning)
  2. Fast EMA > slow EMA (uptrend)
  3. Fresh EMA crossover within lookback window
  4. RSI below oversold threshold or above 55 (momentum)
  5. Price above SMA(20)
  6. MACD histogram positive

STRONG_BUY Upgrade

A BUY is upgraded when both of these confirm:

  • Volume exceeds 1.5× the 20-bar average
  • Price aligned with SMA(50)
ℹ SELL and STRONG_SELL are the mirror: bearish indicators dominate. Same thresholds, opposite direction.
03

Exit Logic

Positions close the moment any single exit condition fires. First trigger wins.

ℹ Dual cadence. Exits are checked twice: every 15 min in the main scan (uses last-bar close), and every 1 min in runExitCheck() using a live quote. The 1-min loop now runs in every mode — not just intraday — so trailing stops track the live peak instead of yesterday's close. A double-sell guard (pendingExits set on engine state) prevents the two intervals from racing on the same symbol.
◼ Fixed Stop Loss— price drops below entry × (1 − stopLossPct)
◼ Dynamic Trailing Stop— price drops below peak × (1 − trailPct)
◼ Take Profit— price exceeds entry × (1 + takeProfitPct)
◼ Sell Signal → Stop-Tighten— a SELL/STRONG_SELL no longer exits at market (demoted 2026-07-14). It raises the stop to price × (1 − trail × ½) on SELL or × (1 − trail × ⅓) on STRONG_SELL, floored at a 1% trail and never lowering an existing stop. A genuine breakdown exits via the tightened stop; a whipsaw survives. (Prod history: 30 signal exits, 1 winner, −$2,717 vs trailing stops +$2,814.)
◼ Hold Period Expired— position held longer than max hold bars
ℹ Corporate actions (splits) — preventive. The engine avoids holding through splits entirely (added 2026-07-15): announced splits are pulled from the broker's corporate-actions calendar daily; new BUYs are refused once a symbol's ex-date is within 5 calendar days (split_blackout), and held positions exit at market on the last trading day before the ex-date (pre_split_exit, weekend-aware). A split doesn't change position value, but brokers cancel open GTC protective stops on the ex-date — holding through means an unprotected window.
ℹ Corporate actions (splits) — reactive safety net. For unannounced or missed actions: the broker sync detects a split signature (share count moved >10% while total cost basis stayed conserved within 2%) and rescales entry/stop/take-profit/peak in place instead of treating it as a trade. The 1-min exit check re-verifies against the broker before firing any stop on a quote below 60% of tracked entry, and the reconciler corrects the basis when an entry/fill ratio lands on an integer split ratio. Added 2026-07-14 after a 4:1 split booked a phantom −$2,829 loss and tripped a daily-loss halt.

Optimized GA — Individual Exits + Post-Exit Redeploy

Each position is managed independently. On every scan (~15 min), the engine checks all 5 exit conditions in priority order. First trigger wins. SPY health filter only blocks new entries — it does NOT force exits of held positions.

  1. Stop loss — price ≤ pos.stopLoss. Initialized at entry × (1 − stopLossPct) — GA-tuned, typically ~8.5%. Ratcheted up to entry × 1.001 once unrealized profit crosses +2% (see Dynamic Trailing Stop § Breakeven-Promote).
  2. Take profit — price ≥ entry + ATR(14) × multiplier (adaptive) or fixed % fallback. Graduates instead of exits: first crossing locks pos.stopLoss to entry × 1.30 (the +30% floor). Subsequent scans hold until weakness signals fire (2-of-3: volume contraction, plateau, RSI rollover). See § Take-Profit Graduation.
  3. Trailing stop — price ≤ peak × (1 − dynamicTrailPct). Tightens exponentially as profit grows
  4. Hold period — position held ≥ holdPeriod trading days. GA-tuned, typically ~33 days
  5. SELL/STRONG_SELL signal — analyzeBars() with GA-tuned signal params scores bearish
ℹ Post-exit redeploy (swap-sell). When a scan exit fires, the freed slot doesn't sit idle until the next 15-min tick. Inside the same scan, any STRONG_BUY candidates that hit the position cap before the exit happened are deferred; after the per-symbol loop ends, the top deferred candidates (by analyzer confidence) get bought to redeploy that capital. Closes a stair-step of ~5-15% per cycle that was lost waiting for the next scan. See MODE_SWAP_SELL_DEFAULT — opt-in per mode (optimized enabled; tactical-smart uses its own pair-wise swap-sell elsewhere).

Tactical Smart — Market Regime + Swaps

Two layers of exit logic:

Layer 1 — SPY Weakness (portfolio-wide)

SPY closes below its 20-day SMA for 3 consecutive days → sell ALL positions immediately at market. No graduated exit. This is the primary exit mechanism and overrides everything.

Layer 2 — Active Management (while SPY is healthy)

While invested, scans every 15 min for held positions with SELL/STRONG_SELL signals (weak stocks). Sells them at market and buys STRONG_BUY replacements. Can also add new positions if cash is available (up to 1.5× maxPositions). Individual stop/TP/trail levels exist (12% / 50% / 11.7%) but with a 999-day hold period, SPY weakness almost always fires first.

Tactical — Pure Market Timing

Simplest exit of all three modes. Primary trigger: SPY below 20-day SMA for 3 consecutive days → sell ALL positions at market. No sell-signal management, no active swapping. Full in or full out at the portfolio level — the only buy/sell decision is SPY trend direction. Re-entry when SPY recovers above 50-day SMA.

⚠ Per-position safety stops still apply. Tactical and tactical-smart entries set stopLoss = entry × 0.88 (12% disaster), takeProfit = entry × 1.5 (50%), and trailingStopPct = 11.7% on the position. The 1-minute runExitCheck loop runs in every mode and will exit a position if these trigger, independent of the SPY trend. Breakeven-promote ladder is disabled on tactical and breakeven-only on tactical-smart (see § Breakeven-Promote per-mode opt-out). The SPY weakness exit is still the primary mechanism — individual stops are catastrophe protection, not first-line.
ℹ Key distinction: In Optimized GA, a SELL signal exits the position; the freed slot is then redeployed into the highest-confidence deferred STRONG_BUY same scan (swap-sell). In Tactical Smart, a SELL signal swaps the position directly for a stronger stock as a pair-wise operation. In Tactical, sell signals are not used at all. Optimized and Tactical Smart converged in PR 14's Option 2 rollout — the remaining differences are per-symbol GA tuning, fixed vs inverse-vol position sizing, and finite vs 999-day hold periods.

Dynamic Trailing Stop

The trailing stop tightens exponentially as profit increases, locking in more gains as the trade runs. Floor is always 2% — the stop never gets tighter than that.

trail = floor + (baseTrail − floor) × e−3 × profitPct

Base is volatility-aware

With per-symbol ATR available, base trail starts at min(25%, 2.5 × ATR / peakPrice) rather than the preset's flat trailingStopPct. Capped at 25% to protect against penny-stock ATR explosions.

Rate is momentum-aware

Decay rate scales with RSI: strong momentum (RSI > 50) slows the tightening (let the trend run); weakening (RSI < 50) speeds it (lock before the pullback). Bounded ±30% of the base rate of 3.

Drawdown-from-peak tightening

Once price has pulled back from the peak by more than 1/2 of the current trail width, an extra tightening factor kicks in — trail collapses toward floor proportionally to the pullback severity.

Breakeven-Promote (Tiered Fixed-Stop Ratchet)

Independent of the trailing stop. As unrealized profit grows, pos.stopLoss ratchets up through four tiers — each tier locks in a portion of the gain. The dynamic trail keeps doing its thing on top; the effective stop on any scan is max(pos.stopLoss, trailingStop).

ℹ Why it exists: the trail formula alone doesn't protect against loss until ~+15% profit (below that, trail width > gain ⇒ trail-only stop sits below entry, locking in a loss if it fires). Breakeven-promote fills that gap. At +2%, the position has a hard breakeven floor regardless of where the trail is. Without this layer, a position that ran +5% and reversed gave back the gain plus ~6.6% (one of the giveback rows in the trail table above) before the trail-only stop caught it. With it, the floor caps the giveback at breakeven once initial conviction is shown.

The ladder is one-way: pos.stopLoss only moves up. A position that skips intermediate tiers (gap up overnight, fast intraday run) promotes directly to the highest qualifying tier.

Dedicated stop-sync scheduler (PR #4, 2026-05-26)

A standalone stop-sync-scheduler.ts now runs every 5 minutes independent of scan health, iterates every running engine, and pushes any in-memory ratchets to the broker. Mirrors the shape of engine-watchdog.ts (start/stop lifecycle, globalThis-tracked setInterval, wired into instrumentation.ts at boot).

  • Cadence: 5 min — tight enough that a fresh breakeven promotion reaches the broker within at most 5 min, loose enough to avoid 12× the replaceOrder calls per hour vs the previous per-scan cadence
  • Per-user gates in syncBrokerStopsForUser(): engine exists + running + has positions + no scan in flight. The last gate prevents racing the in-scan sync at the scan tail when scans are healthy. Halt intentionally does NOT gate this path — the helper only places/replaces sell-side GTC stops (never opens positions), and halting it would freeze broker stops at their last value the moment the engine halts, which is the exact scenario where keeping stops fresh matters most
  • Mode-agnostic — runs for tactical / tactical-smart / optimized / conservative / moderate / aggressive / adaptive identically. The in-scan syncBrokerStops() calls at scan tails remain as redundant backup; they fire when scans complete cleanly. The scheduler is the always-on safety net
  • Bootstrap — fires one immediate cycle at container start (in addition to the 5-min interval) so a fresh deploy picks up where the previous container left off without waiting 5 min

Net effect: regardless of mode or scan health, in-memory pos.stopLoss reaches the broker within 5 min of being set. A breakeven-promote that fires at +2% on the 1-min poll becomes a live broker GTC stop within the next 5-min scheduler tick.

Take-Profit Graduation

For modes where graduation is enabled (tactical-smart and optimized — see MODE_GRADUATION_DEFAULT), the pos.takeProfit threshold is no longer a hard exit — it's a graduation point.

  1. First crossing → lock pos.stopLoss to entry × 1.30 (the +30% graduation floor). Never lowers an existing higher stop — if the dynamic trail already ratcheted past +30%, no-op.
  2. Subsequent scans → shouldGraduateExit() evaluates 3 weakness signals:
    • Volume contraction: 5-day avg volume < 20-day avg × 0.85
    • Plateau: within 2% of the 10-bar peak (still under it — not extending new highs)
    • RSI rollover: rsi_14 < 60 (was overbought, no longer)
  3. 2-of-3 fires → exit with reason Graduated exit at +X%: N/3 weakness signals. Otherwise hold; regular stop_loss + trailing + SELL signal still apply via the exit chain.
ℹ Why graduation is enabled for optimized too (PR 14): the GA-tuned takeProfit was found on a finite training window. In trending out-of-sample markets, GA exits proved too tight — the position got clipped at +50% (or whatever the GA found) while the underlying ran to +100%+. Graduation converts that "best historical exit" into "minimum guaranteed +30% with unlimited upside, gated by real-time weakness." The same logic that won for tactical-smart on DELL/MU/SNDK winners now applies to optimized's per-symbol picks.

Dual-Layer Stop Protection

Two layers of stop orders protect positions depending on whether the engine is running:

  • While running (protective stops): Gain-aware GTC stop orders on Alpaca using max(disasterStop, trailingStop, fixedStop) with current broker price as peak. Positions with unrealized gains get tight trailing stops, not a flat 18% from entry. syncBrokerStops() ratchets stops up every scan cycle as price rises.
  • When stopped (safety stops): Tighter strategy-level GTC stops (~8.5% from optimizer) placed on Alpaca. More protective since the engine won't be managing exits.
  • On engine start: Cancels old stops → places gain-aware protective stops.
  • While running: syncBrokerStops() updates stops every scan to match dynamic trailing (2% floor, exponential decay from base).
  • On engine stop: Cancels protective stops → places ~8.5% safety stops.

Auto-Restart After Deploy

On container start, instrumentation.ts waits 5s for the DB pool, then runs bootEngines() which iterates every user with an active broker connection and calls autoStartIfNeeded(). The engine resumes without waiting for a user to open the dashboard. Transient broker/DB errors retry up to 3 times with 2s/4s backoff before giving up at error level.

Engine-state snapshot rehydration. Beyond mode, the engine restores its in-RAM safety counters from trader_engine_snapshot (migration 0040, one JSONB row per user): position map, dailyLoss, dailyNotional, consecutiveLosses, cooldowns, pendingExits, recentOrderTimestamps, exitRejectionCount, exitSuppressedUntil, unprotectedSymbols, and boot-equity snapshot. Written at the end of every successful runScan (best-effort — a failed write doesn't abort the scan). Snapshots older than SNAPSHOT_MAX_AGE_MS (60 min) are discarded on hydrate — broker is authoritative past that. Versioned payload (v: 1); deserialize returns null on version mismatch so a future-schema snapshot doesn't crash boot. A successful hydrate emits an ENGINE_STARTED audit row with metadata.origin: "snapshot_hydrate". Without this, only mode survived a deploy — a redeploy mid-halt would have cleared the consecutive-loss counter and daily notional cap, effectively re-arming the engine after the very protections that had fired.

Graceful Shutdown

SIGTERM and SIGINT handlers call shutdownAllEngines() — for each running engine, it clears the scan/exit-check intervals and runs placeSafetyStops() so every position has a tighter GTC stop on Alpaca before the process exits. Hard 8s budget, well under podman's 10s grace period — if the broker is slow, the handler force-exits rather than block the rebuild.

Mode Persistence

The current mode is saved on every heartbeat as paper:optimized, paper:tactical, etc. Auto-restart reads this to resume the correct mode. Valid modes: conservative, moderate, optimized, aggressive, tactical, tactical-smart, adaptive.

Halt Semantics — What Halt Blocks And What It Doesn't

Halt (engine.halted = true) is a buy-side circuit breaker, not a global engine freeze. The intent is “stop digging deeper” — block new positions while continuing to manage the ones already open. A halt that simultaneously stripped exit protection from losing positions would be the inverse of safe.

Halt blocks (BUY-side):

  • runScan (15-min main scan) — early-return; no entries, no swap-sells, no add-to-position
  • runTacticalSmartScan — same
  • Main scan's setInterval callback — early-return so the scan body never starts
  • pushExternalSignal / broadcastExternalSignal — refuses new screener signals

Halt does NOT block (protective / SELL-side):

  • runExitCheck (1-min poll) — keeps honoring trailing-stop / stop-loss / take-profit on existing positions; updates pos.peakPrice; promotes breakeven; places market-sell exits
  • syncBrokerStopsForUser (5-min standalone scheduler) — keeps pushing ratcheted pos.stopLoss to Alpaca as GTC orders, so the broker side stays in lockstep with the in-memory side
  • Existing GTC broker stops at Alpaca — tripSafeguardHalt() never calls cancelOrder; whatever stops are at the broker stay there and continue to fire on price triggers

Why this asymmetry matters: the most dangerous moment for an unmanaged position is right after a halt — that's the exact window where conditions are deteriorating and stops need to be tightening, not freezing. The pre-2026-06-04 design halted everything, which meant a halted engine that subsequently lost its broker stops (e.g., from a placeDisasterStops-then-halt-re-trip restart sequence) would orphan every position with no protection at all until manual intervention. The current design keeps the protective layer alive so existing positions self-resolve through normal exit triggers regardless of halt state.

Streak-Halt Auto-Recovery (Daily-Loss + Consecutive-Losses)

Two streak halts — daily_loss (realized losses exceed dailyLossPct × equity) and consecutive_losses (N losing trades in a row, default 5) — are intraday-scope signals: their counters reset at the new trading day boundary, so the halts that derived from those counters reset too.

Cross-day auto-recovery (expanded 2026-06-12 to cover consecutive_losses): on the next trading day's first scan, maybeClearDailyLossHaltOnDateRollover clears the halt and prunes matching errors. engine.consecutiveLosses is also zeroed — without this, a snapshot rehydrate would re-trip the halt on the first new-day loser. autoStartIfNeeded recognizes both as stale-clearable. Integrity halts (account_mismatch, equity_collapse, broker_unreachable, user_emergency_halt) do NOT clear — they require explicit user Start.

Same-day regime-gated auto-resume (consecutive_losses only, 2026-06-12): a streak halt can fire early in a regime-driven selloff — five picks blow up because SPY dropped with them, not because the strategy broke. maybeClearConsecutiveLossesHaltOnRegime fires when ALL of: (1) halt reason is consecutive_losses, (2) ≥ 30 min since halt (no instant flap), (3) SPY intraday drop (open → current) > 1.5%. On trigger: in-memory halt cleared, counter zeroed, today's trader_daily_pnl.halted explicitly de-escalated (bypasses the sticky-OR in upsertDailyPnl), ENGINE_HALT_AUTO_RESUMED audit row written. Defensive: NaN / zero / negative SPY feeds fail closed; SPY fetch errors fail closed. Does NOT apply to daily_loss — that's a hard cumulative cap, not a streak signal.

Both gates wired into runScan, runTacticalScan, and runTacticalSmartScan, between the rollover clear and the halted early-exit.

PENDING-Row Reconcile (2026-06-12)

reconcilePendingTrades walks PENDING trader_trades rows with a broker_order_id, looks each up at the broker, writes back fill price / time / corrected P&L / final status. Two failure modes from the admin 2026-06-09 incident drove a rework:

  • Lookback widened 24h → 7d (RECONCILE_LOOKBACK_MS). A 5-loss consecutive_losses halt suppressed runScan — the only reconcile caller — for ~50h. By restart the 3 trailing-stop sells from 06-09 had aged out of the 24h query window and stayed PENDING forever despite the broker having filled them.
  • Per-id getOrder(orderId) fallback. The getOrders(200) batch can miss old ids in high-volume accounts or after a long gap. Now: not in batch → per-id GET. Broker 404 → terminal "purged"; transient error → leave PENDING for next cycle.
  • Three call sites instead of one. runScan/runTacticalScan/runTacticalSmartScan (unthrottled, 15-min cadence, halt-gated); runExitCheck (5-min throttle via engine.lastReconcileAt; bypasses halt — this is the path that closes the gap admin's incident exposed); startEngine (fire-and-forget sweep right after engine.running = true, catches up anything stranded by the prior halt window).

One-off cleanup for rows stranded before this change shipped: scripts/reconcile-stuck-trades.ts (dry-run by default, --apply to write). Uses per-id getOrder for every row, so it works regardless of how old.

Long-Only Enforcement

The engine never opens shorts — entry logic only fires on BUY/STRONG_BUY. If a short shows up on the broker (manual order, external tool), syncPositionMapFromBroker() filters it out so long-only stop math doesn't get applied wrong-direction to it. The screener also no longer pushes SELL/STRONG_SELL into the engine queue.

Exit Race Protection

The 1-min live-quote exit check and the 15-min main scan both call placeOrder({side:"sell"}). A pendingExits: Set<symbol> on engine state gates both code paths — add() before placing the sell, delete() in finally. Prevents the double-sell that previously surfaced as Alpaca rejecting a second order with "insufficient qty".

Cooperative Scan Cancellation

The runScanGuarded watchdog overrides any scan still running past 10 minutes (STALE_SCAN_OVERRIDE_MS). Without cancellation, the orphaned scan kept executing in the background, racing the new one and mutating shared state (position map, daily notional, cooldowns). Each scan captures myGeneration = ++engine.scanGeneration at start; the 10-min override bumps the counter; the stale scan calls throwIfScanCancelled(engine, myGeneration) at every major yield point (after enforceDailyLossHalt, between per-symbol iterations, before the swap-sell post-loop block) and throws ScanCancelledError if its generation no longer matches. runScan / runTacticalScan / runTacticalSmartScan catch it at the top level and exit cleanly — no error row, no audit pollution. In-flight HTTP requests the stale scan already issued still complete, but their results land on the floor (the engine just stops acting on them).

Tactical Modes

Tactical modes don't pick individual stock signals. They use SPY as a market barometer — fully invested when the market is trending up, fully out when it breaks down.

Tactical (Equal Weight)

Entry — Full In

Exit — Full Out

  • Signal score — STRONG_BUY = 4, BUY = 2, HOLD = 0, SELL = −2

  • Confidence — × 2 multiplier

ℹ Top 5 STRONG_BUY candidates are logged to the signals table for visibility, even if not acted on.

Exit

Same as Tactical — full exit on SPY weakness (below 20-day SMA for 3 consecutive days).

Screener vs Engine Authority

The screener only pushes BUY/STRONG_BUY signals to the engine — never SELL signals. Once a position is entered, it is managed entirely by the engine's exit logic. The screener has no influence on exits, stop losses, or take profits. If the screener and engine disagree on a stock (they use different signal params), the engine's analysis controls the position.

GA Diversity Mechanisms

Diversity is purely a GA search mechanism — it has no effect on live trading. It controls how the optimizer explores the 8-dimensional parameter space.

  • Diversity measurement: Average normalized distance across sampled parameter pairs (0 = clones, ~1 = max spread)
  • Adaptive mutation: Rate scales from 10% (healthy, diversity > 0.35) → 20% (baseline) → 50% (collapsed, diversity < 0.10)
  • Random immigrants: 5% of each generation replaced with fresh random individuals
  • Stagnation restart: After 8 gens without improvement, inject 15% immigrants + max mutation
  • Convergence chart: Best, average, and diversity lines shown per generation on dashboard

GA Fitness — Train-Only with Risk Multipliers

fitness() scales excessReturn by two risk multipliers — sharpeMult = min(sharpe / 1.0, 1.0) and drawdownMult = max(0, 1 − maxDrawdown / 30). maxDrawdown is a percent; an earlier /0.20 was a percent/fraction unit bug that floored the term to ~0.05 — effectively no risk control. Fixed 2026-05-28. Multipliers apply only to positive returns (otherwise the GA preferred worse-risk-profile losers) and are floored at 0.05 so the GA still has gradient at extreme drawdowns.

Train-only fitness (2026-05-28). Fitness is now evaluated on the training window only. The previous blend 0.6 × train + 0.4 × test leaked the holdout into selection — the GA literally optimized the "test" return, so test ≈ train and the reported OOS number was meaningless. The test window is now scored once on the final winner and reported as a genuine out-of-sample number. Re-run the optimizer after deploying this change; expect honest (much lower) test returns. The Mode-Comparison "Optimized" row uses the run's stored OOS metrics directly so it lines up with the test-segment number on the run-detail page.

Backtest Realism — Cost Model + Survivorship

Both backtesters — single-symbol runBacktest and the optimizer's portfolioBacktest — now apply a shared cost model (BACKTEST_COSTS in src/lib/config.ts):

  • Per-side slippage in bps (default 5 bps): buys fill above the trigger, sells below it. Entry slippage is carried in the cost basis so realized P&L reflects it.
  • Per-fill commission (default $0): subtracted from net proceeds.

Before this change (pre-2026-05-28) both backtesters were frictionless, which compounded a tiny per-trade edge into fantasy returns (900–1300% test windows vs a roughly flat-market buy-and-hold). Together with the drawdown-unit fix and train-only fitness above, GA fitness now reflects realistic risk-adjusted performance. Re-run the optimizer after any cost-model change — fitness landscapes shift and existing best-params are no longer the best on the new objective.

Survivorship bias — partially fixed (2026-05-29). The sp500 universe now uses point-in-time membership: getSP500MembershipResolver() (src/lib/sp500.ts) reconstructs date → constituents from Wikipedia's changes table walked backward from today's list, and portfolioBacktest gates entries to then-members via eligibleOn(date). The top50 / top150 universes are hardcoded today's-winners lists with no PIT data — those remain biased (the full-history guard drops mid-window IPOs; the UI labels them biased and defaults to sp500). Residual: fully-delisted names have no free Yahoo price data, so they still drop out — survivorship is reduced, not eliminated. Treat backtest returns as relative scores; validate via paper trading.

Wash-Sale Protection

When enabled (MTM unchecked), the engine blocks BUYs on any symbol with a losing exit in the last 31 calendar days. One day past the IRS 30-day rule for safety margin.

  • Source query: SELECT DISTINCT symbol FROM trader_trades WHERE user_id=? AND action IN ('SELL','manual_close') AND pnl < 0 AND created_at > now() - 31 days
  • Cached for 5 min on engine state as washSaleBlockedSymbols: Set<string> — one batched DISTINCT query per refresh, O(1) lookup per BUY.
  • Symbol-level, not lot-level: one partial losing close blocks the whole ticker for 31 days. Over-conservative, but simpler and safer than per-lot accounting.
  • Manual closes count: the Trader UI's Flatten command logs action="manual_close" in trader_trades; those also feed the wash-sale set.
  • Does NOT catch: manual BUYs through Alpaca's own app (engine sees them only after position sync, too late to block); "substantially identical" ETFs (SPY ↔ IVV); different share classes (GOOG vs GOOGL).

How it used to work (pre-2026-06-04):

  1. Auto-detection. Read account.equity < $25,000, the broker-reported daytrade_count, and the pattern_day_trader flag from getAccount() on every scan. evaluatePdtState(engine, account) reconciled engine state with the live snapshot.
  2. Mid-session re-evaluation. Transition not-vulnerable → vulnerable emitted one engine.pdt_vulnerable audit event and flipped the Trader-page warning panel.
  3. Buy-block. When pdtVulnerable AND daytradeCount >= 3 (one shy of the 4-trade flag), new BUYs were blocked with audit reason pdt_protection. SELLs were never blocked.

How it works now (post-2026-06-04):

  • FINRA Rule 4210 amendments: the PDT designation is eliminated, the $25,000 minimum equity drops to the standard $2,000 margin floor, the 5-day day-trade counter is abolished, and brokers move to real-time intraday margin checks instead of end-of-prior-day buying-power calculations.
  • Alpaca aligned the same day: pattern_day_trader now returns false, daytrade_count returns 0, and both fields are scheduled for full removal from the API on 2026-07-06. "Day Trade Buying Power" is replaced by "Intraday Buying Power"; orders that would create or increase an Intraday Margin Deficit (IMD) are rejected pre-trade.
  • Sentinel changes: PDT_EQUITY_THRESHOLD, PDT_DAYTRADE_BUY_BLOCK, evaluatePdtState(), the canPlaceBuyOrder() PDT branch, the pdtVulnerable / pdtDayTradeCount / pdtPatternFlagged engine state, the engine.pdt_vulnerable audit transition, and the corresponding Trader-page warning banner are all gone. The daytradeCount / daytradeBuyingPower / patternDayTrader fields are no longer mapped from the broker.
  • Reactive handling preserved: Alpaca's legacy PDT rejection code 40310100 may still appear during the API-removal transition. isPdtRejection() still matches it; recordExitRejection() still increments a per-symbol counter; EXIT_REJECTION_THRESHOLD consecutive rejections still suppress retries for 30 min and surface the symbol on the unprotected-positions banner. Audit enum ENGINE_PDT_VULNERABLE is preserved (no longer emitted) so historical rows still resolve.
ℹ Cash accounts were never subject to the PDT rule (no margin, so the 5-day counter and $25k floor did not apply); their settlement-cycle rules are unchanged by the 2026 amendment.

Audit Log

Append-only, hash-chained, tamper-evident record of every privileged action. Schema in drizzle/0016_audit_log.sql; helper in src/lib/audit.ts; admin viewer at /dashboard/admin/audit.

Row Shape

One row per event with the actor, action, resource, IP / user-agent, structured metadata, and the hash-chain pointers:

id (bigserial) prev_hash (text) created_at (timestamptz) hash (text) actor_user_id (uuid) ip (text) actor_email (text) user_agent (text) actor_role (text) metadata (jsonb) action (text) resource_type (text) resource_id (text)

Hash Chain

Each row's hash is the SHA-256 of its predecessor's hash plus its own canonical fields:

hash = sha256( prev_hash || \0 || created_at.toISOString() || \0 || actor_user_id || \0 || action || \0 || resource_type || \0 || resource_id || \0 || canonical_json(metadata) )

NUL byte separator cannot occur in any UTF-8 string field, preventing field-confusion / length-extension attacks. canonical_json sorts keys at every depth so equivalent objects produce identical hashes.

The genesis row's prev_hash is the literal string "GENESIS". Tampering with any row breaks the chain at that row when verified.

Write Path

writeAudit() opens a Postgres transaction, takes pg_advisory_xact_lock(8493920100) (auto-released on commit), reads the tail row's hash, computes the new hash, inserts. Concurrent writers serialize on the advisory lock so the chain can't fork.

The helper never throws — failures log and return null. Audit problems must not cascade into request failures (rather lose a log line than refuse a legitimate trade).

The admin viewer at /dashboard/admin/audit has a "Verify chain" button that calls POST /api/admin/audit/verify. The endpoint walks every row in id order, recomputes each hash, and reports either "intact" or the first row where the chain breaks (with stored vs expected hash). Walk takes ~2s per 100k rows.

Run it after any unusual incident, before any major decision based on the trade history, or as a periodic sanity check.

Going Live & Rollback

Going Live

  1. Tighten risk profile (Trader page → Risk Settings). For a $5k cash-only account: maxPositionPct=25−33%, maxDailyLossPct=2%, maxDailyNotionalPct=0.5, maxConsecutiveLosses=3, maxPositionSize=20, maxExposureMultiplier=1.0.
  2. Add live broker connection (Settings → Add Broker). Environment = Live, paste live Alpaca API key+secret, type "LIVE" in the confirmation input, Test, Save.
  3. Deactivate paper connection (Settings → toggle isActive=false on the paper row). Engine then resolves only the live one.
  4. Flip the env-gate on the droplet:
    echo 'ALLOW_LIVE_TRADING=1' | sudo tee -a /opt/apps/sentinel/.env sudo podman stop sentinel-app && sudo podman rm sentinel-app sudo podman run -d --name sentinel-app --network=host \ --env-file /opt/apps/sentinel/.env \ -e NODE_ENV=production -e HOSTNAME=0.0.0.0 -e PORT=3010 \ -e NEXT_TELEMETRY_DISABLED=1 -e CACHE_DIR=/data/cache \ -v /opt/apps/sentinel/cache:/data/cache:Z \ --restart always -m 2g \ ghcr.io/beacontry/sentinel:latest

    podman restart does NOT re-read env-file — must stop && rm && run.

  5. Start engine (Trader page → Start) in a swing mode. Watch the persistent red LIVE banner appear, audit log fill with engine.started (metadata.environment="live"), and the boot equity snapshot get captured.

Rollback — Three Off-Ramps

A. Env-only rollback — "live went badly, go back to paper"

Cheapest path. No code changes, no rebuild, no DB changes. Clear ALLOW_LIVE_TRADING in /opt/apps/sentinel/.env, recreate container (same podman run as above). Engine immediately refuses live boots; live broker row stays in DB for easy re-enable.

B. Code revert — Phase 3 false halts / audit too slow

git revert phase commits in reverse order (4 → 3 → 2). Migrations stay applied (additive). Do not revert Phase 1 — it would re-introduce the silent-plaintext decrypt fallback. Phase 4 depends on Phase 2 (audit viewer reads the table), so revert 4 before 2.

C. Migration drop — only when table is corrupted

Almost never needed. Always pair with the matching code revert or loadRiskLimits() crashes on every scan. For audit_log: TRUNCATE audit_log is the clean reset (next write becomes new genesis). Do NOT DELETE WHERE id < N — that breaks the hash chain forever.

What to Watch in the First Hour

  • Red LIVE banner missing. engine.environment not captured at boot. Stop engine, check the engine.started audit row metadata; restart engine.
  • PDT panel missing. Expected post-2026-06-04 — the FINRA Pattern Day Trader rule was retired and the Trader-page banner was removed alongside it. Alpaca's daytrade_count / pattern_day_trader fields will be deleted from the API on 2026-07-06.
  • Many order.rejected rows with insufficient_buying_power. Live broker margin/cash strictness. Tighten positionPct if persistent.
  • Chain verify reports a break. Stop immediately. Do not trade. Investigate before resuming — this is the critical evidence trail.
  • First buys filling at unexpected prices. Real slippage between paper assumption and live execution. Document the delta — that's your paper-to-live tax.

Adaptive Engine Mode

EngineMode includes "adaptive". When a user selects adaptive, the engine reads market regime at each scan boundary and runs as one of conservative / moderate / optimized / aggressive underneath. The user-selected mode stays "adaptive"; strategy decisions go through getActiveMode(engine) which returns the effective base mode. (tactical is excluded from adaptive's targets — its all-in/all-out philosophy contradicts a regime classifier that would switch off it.)

Regime classifier

Pure function in src/lib/market-regime.ts. Input: { vix, spyPrice, spyMA50, spyMA200, breadthScore? }. Output: { regime, recommendedMode, reasons }.

Regime rules (v1)

  • risk_off → conservative. VIX > 28 OR SPY < SMA50
  • neutral → moderate. 18 < VIX <= 28 AND SPY >= SMA50
  • risk_on → optimized. VIX <= 18 AND SPY > SMA50
  • strong risk_on → aggressive (live only). VIX <= 14 AND SPY > SMA200 AND breadth > 75

Never auto-selected: tactical (all-in/all-out contradicts a regime classifier that would switch off it), tactical-smart (already adaptive in its own way), adaptive itself (self-reference loop).

Engine wiring

refreshAdaptiveMode(engine) runs at the top of each scan path (main + tactical-smart). Fetches ^VIX + SPY bars via the existing market-data provider, computes SPY SMA50/200, calls detectMarketRegime, sets engine.effectiveMode + engine.adaptiveRegime. Emits ENGINE_MODE_SWITCHED audit row only when effectiveMode actually changes scan-to-scan.

Backtester

runBacktest(symbol, bars, ..., mode?, marketContext?) accepts optional mode + marketContext: { spyBars, vixBars }. When mode === "adaptive" AND marketContext provided, the backtester re-resolves the effective config per bar (looks up SPY/VIX for that date, runs the classifier, swaps BacktestConfig). Returns modeTimeline: { date, mode }[] so the UI can visualize regime swings.

Mode-compare page

/dashboard/backtest/mode-compare?symbol=AAPL runs the 3 user-selectable comparable modes (optimized / tactical / adaptive; tactical-smart excluded as its active-management logic doesn't translate to backtesting) in parallel via Promise.allSettled. Returns stats + equity curves + adaptive's modeTimeline.

Trader page status banner

When running adaptive, two lines under the controls: a standard "Running (adaptive) · PAPER · N scans" line, plus an adaptive-specific second line showing the effective mode + regime: "Adaptive — currently optimized · VIX 18.2 · SPY +1.2% vs SMA50 · risk_on".

Failure handling

If VIX/SPY fetch fails, engine keeps the previous effectiveMode (does NOT halt — adaptive is a meta-decision, not a safety check). Logs a warning.

Live vs backtest difference

Live mode uses VIX + SPY only — refreshAdaptiveMode() does NOT fetch breadth (a full breadth scan = 50 stocks × N days, kept as a v2 enhancement; the cost would land on every scan tick). The strong-risk-on → aggressive bump in the classifier requires a breadth score, so in practice live adaptive can resolve only to conservative, moderate, or optimized. Backtest replays VIX + SPY only too. Defensible simplification — if you specifically want aggressive sizing in a strong bull, pick it directly instead of relying on adaptive.
