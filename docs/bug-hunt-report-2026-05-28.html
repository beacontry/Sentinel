Trading engine — concurrency & safety

BugSevWhere
Double-sell race — the 15-min scan and 1-min exit poll each did a stale pendingExits.has check, then awaited, then claimed; both could fire a market sell on one position (oversell into a short) + double-count daily loss. Added an atomic synchronous re-check immediately before the claim in both paths.P0trading-engine.ts
Double-start interval leak — startEngine checked running but set it only after 3 awaits, so two concurrent starts orphaned a scan-loop interval. Added a synchronous starting claim cleared on every exit path (incl. the DB-throw path).P1trading-engine.ts
flatten-all could double-sell with the running engine — added reserveManualFlatten() to reserve symbols in pendingExits for the flatten's duration (no-op when stopped), released on success and on the outer catch.P2trading-engine.ts, trader/command/route.ts
Per-user engine state never evicted — stopEngine cleared timers but left EngineState/position-map/broker-cache in the globalThis maps forever. Added a guarded, deferred eviction (past the max scan window, re-checks still-stopped).P2trading-engine.ts

Known limitation — noted, not fixed (needs a feature-level change)

The alerts engine (alert-engine.ts) has two structural issues that warrant a focused PR rather than a patch: (1) rules are evaluated only as a side-effect of GET /api/analyze/[symbol] and keyed by symbol (not user), so an alert fires/cooldowns based on whoever happens to analyze the symbol — and a symbol nobody analyzes is never checked (missed alerts); (2) "crossover" rule types are really level checks (fire while-above, not on the cross). The proper fix is a scheduled per-user alert evaluator with crossing-state tracking.
